# 단계별 개발 기록

각 단계에서 **무엇을 만들었는지**, **구조(아키텍처)에 어떤 개념이 새로 생겼는지**를 정리한 문서예요.
코드를 한 줄씩 읽지 않아도 이 문서만으로 앱의 뼈대를 이해할 수 있게 쓰는 것이 목표예요.

---

## 1단계 — 레이아웃과 홈 화면

**만든 것:** 헤더, 사이드바, 카테고리 칩, 영상 카드 그리드

**새 개념: 층 나누기 (Layered Architecture)**

```
화면 층   web/        React 컴포넌트
서비스 층 core/videoService.ts
데이터 층 core/data/
```

- 화면은 서비스 함수(`getVideos`)만 부르고, 데이터가 어디 있는지는 몰라요.
- `core/`는 React를 전혀 쓰지 않는 순수 TypeScript예요. 그래서 모바일 앱(React Native)으로 그대로 옮길 수 있어요.
- 서비스 함수는 가짜 데이터를 쓰는데도 일부러 `Promise`(비동기)로 돌려줘요. 나중에 진짜 서버로 바꿔도 화면 코드가 그대로 동작하게 하려는 거예요.

**새 개념: 컴포넌트**

화면을 레고 블록처럼 쪼개요. `HomePage` 안에 `VideoCard`가 있고, `VideoCard` 안에 `Thumbnail`이 있어요.
같은 블록(`Thumbnail`)을 여러 곳에서 다시 쓸 수 있어요.

## 1.5단계 — YouTube 다크 모드 디자인

**새 개념: 디자인 토큰**

색과 크기를 CSS 맨 위에 변수로 모아 둬요(`--bg`, `--header-h` 등).
컴포넌트는 `#0f0f0f` 같은 색을 직접 쓰지 않고 변수 이름만 써요.
그래서 테마를 바꿀 때 변수 값만 바꾸면 돼요(5단계에서 실제로 활용).

---

## 2단계 — 영상 시청 페이지

**만든 것:** `/watch/영상ID` 주소의 시청 페이지(플레이어, 제목, 채널, 좋아요·공유 버튼, 설명란 더보기), 오른쪽 추천 영상 목록, 없는 주소용 404 페이지, 시청 페이지 전용 서랍형 사이드바

**새 개념: 라우팅 (Routing)**

```
주소창              →  보여줄 페이지
/                   →  HomePage
/watch/v3           →  WatchPage (videoId = "v3")
그 외               →  NotFoundPage
```

- `App.tsx`의 `<Routes>`가 이 "주소 → 페이지" 표 역할을 해요.
- **주소가 곧 상태**예요. `WatchPage`는 주소에서 `videoId`를 읽어서 그 영상을 보여줘요.
  그래서 새로고침하거나 주소를 복사해서 보내도 같은 영상이 열려요.
- 추천 영상을 누르면 페이지 전체를 새로 받지 않아요. 주소만 바뀌고, React가 바뀐 부분만 다시 그려요.
  이런 방식을 SPA(Single Page Application)라고 해요. youtube.com도 이렇게 동작해요.

**새 개념: 공통 훅으로 반복 없애기 (`web/hooks/useAsync.ts`)**

"요청 → 기다림(로딩) → 응답 저장" 흐름이 페이지마다 반복돼요. 그래서 이 흐름을 훅 하나로 묶었어요.

```ts
const { data, loading } = useAsync(getVideo, videoId);
```

- `videoId`가 바뀌면 알아서 다시 요청해요.
- 응답이 늦게 오는 사이에 다른 영상으로 넘어가면, 늦게 온 옛 응답은 버려요.

**새 개념: 레이아웃 모드**

사이드바는 상황에 따라 세 가지 모양(variant)을 가져요.

| 모드 | 언제 | 모양 |
|---|---|---|
| `full` | 넓은 화면의 홈 | 240px 펼침 |
| `mini` | 좁은 화면의 홈 / 메뉴 접음 | 72px 아이콘만 |
| `drawer` | 시청 페이지, 모바일 | 숨겨 두고, 메뉴 버튼을 누르면 화면 위에 덮어서 열림 |

모드를 정하는 일은 `App.tsx` 한 곳에서만 해요. `Sidebar`는 전달받은 모드대로 그리기만 해요.

**참고:** 샘플 영상은 실제로는 10초짜리예요. 카드에 표시되는 길이(예: 57:03)는 가짜 데이터라서 실제 재생 길이와 달라요.

## 3단계 — 검색

**만든 것:** 헤더 검색창(자동완성, 키보드 ↑↓ 선택, 지우기 버튼), `/results?search_query=검색어` 검색 결과 페이지, 결과 없음 화면, 모바일 전용 검색 모드, 첫 자동 테스트

**새 개념: 검색 상태를 주소에 담기 (URL as State)**

```
검색창에 "요리" 입력 후 Enter
  → 주소가 /results?search_query=요리 로 바뀜
  → ResultsPage가 주소에서 검색어를 읽어 searchVideos("요리") 요청
  → 헤더 검색창도 주소에서 검색어를 읽어서 "요리"를 표시
```

- 검색어를 React 상태 변수가 아니라 **주소**에 저장해요.
  그래서 뒤로가기를 누르면 이전 검색어와 결과로 자연스럽게 돌아가요. 새로고침이나 링크 공유도 그대로 동작해요.
- 헤더와 결과 페이지는 서로 직접 값을 주고받지 않아요. 둘 다 **같은 주소를 읽을 뿐**이에요.
  주소가 두 컴포넌트가 함께 보는 "공유 저장소" 역할을 해요.

**새 개념: 비즈니스 로직을 순수 함수로 분리 (`core/search.ts`)**

- 검색 규칙은 모두 `core/search.ts`에 있어요. 모든 단어가 들어 있어야 결과에 포함되고, 제목에서 맞으면 점수가 더 높아요.
- 이 규칙은 화면과도, 데이터가 어디서 오는지와도 상관없는 **순수 함수**예요. 입력이 같으면 결과도 항상 같아요.
- 서비스 층(`videoService.searchVideos`)은 "데이터 가져오기 + 규칙 적용"을 이어 주기만 해요.
  나중에 서버가 생기면 검색 규칙은 서버로 옮기고, 서비스는 서버에 요청만 하게 바꾸면 돼요.

**새 개념: 자동 테스트 (`npm test`)**

- `core/*.test.ts` 파일이 "이 입력이면 이 결과가 나와야 한다"를 코드로 적어 둔 문서예요.
- `core/`는 순수 TypeScript라 브라우저 없이도 테스트할 수 있어요. 층을 나눈 덕분에 얻은 또 하나의 장점이에요.
- 지금 테스트는 9개이고, 모두 통과해요.

**새 개념: `key`로 컴포넌트 새로 만들기**

검색창은 내부에 입력 중인 글자를 상태로 갖고 있어요. 뒤로가기로 주소의 검색어가 바뀌면 검색창도 그 값으로 돌아가야 해요.
이때 `key={검색어}`를 주면, 검색어가 바뀔 때 React가 검색창을 아예 새로 만들어서 깨끗하게 초기화해요.
2단계에서 설명란 "더보기" 상태를 영상마다 초기화한 것도 같은 기법이에요.
