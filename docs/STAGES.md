# 단계별 개발 기록

각 단계에서 **무엇을 만들었는지**, **구조(아키텍처)에 어떤 개념이 새로 생겼는지**를 정리한 문서예요.
코드를 한 줄씩 읽지 않아도 이 문서만으로 앱의 뼈대를 이해할 수 있게 쓰는 것이 목표예요.

---

## 1단계 — 레이아웃과 홈 화면

**만든 것:** 헤더, 사이드바, 카테고리 칩, 영상 카드 그리드

**새 개념: 층 나누기 (Layered Architecture)**

```
화면 층   web/        React 컴포넌트
서비스 층 core/videoService.ts
데이터 층 core/data/
```

- 화면은 서비스 함수(`getVideos`)만 부르고, 데이터가 어디 있는지는 몰라요.
- `core/`는 React를 전혀 쓰지 않는 순수 TypeScript예요. 그래서 모바일 앱(React Native)으로 그대로 옮길 수 있어요.
- 서비스 함수는 가짜 데이터를 쓰는데도 일부러 `Promise`(비동기)로 돌려줘요. 나중에 진짜 서버로 바꿔도 화면 코드가 그대로 동작하게 하려는 거예요.

**새 개념: 컴포넌트**

화면을 레고 블록처럼 쪼개요. `HomePage` 안에 `VideoCard`가 있고, `VideoCard` 안에 `Thumbnail`이 있어요.
같은 블록(`Thumbnail`)을 여러 곳에서 다시 쓸 수 있어요.

## 1.5단계 — YouTube 다크 모드 디자인

**새 개념: 디자인 토큰**

색과 크기를 CSS 맨 위에 변수로 모아 둬요(`--bg`, `--header-h` 등).
컴포넌트는 `#0f0f0f` 같은 색을 직접 쓰지 않고 변수 이름만 써요.
그래서 테마를 바꿀 때 변수 값만 바꾸면 돼요(5단계에서 실제로 활용).

## 2단계 — 영상 시청 페이지

**만든 것:** `/watch/영상ID` 주소의 시청 페이지(플레이어, 제목, 채널, 좋아요·공유 버튼, 설명란 더보기), 오른쪽 추천 영상 목록, 없는 주소용 404 페이지, 시청 페이지 전용 서랍형 사이드바

**새 개념: 라우팅 (Routing)**

```
주소창              →  보여줄 페이지
/                   →  HomePage
/watch/v3           →  WatchPage (videoId = "v3")
그 외               →  NotFoundPage
```

- `App.tsx`의 `<Routes>`가 이 "주소 → 페이지" 표 역할을 해요.
- **주소가 곧 상태**예요. `WatchPage`는 주소에서 `videoId`를 읽어서 그 영상을 보여줘요.
  그래서 새로고침하거나 주소를 복사해서 보내도 같은 영상이 열려요.
- 추천 영상을 누르면 페이지 전체를 새로 받지 않아요. 주소만 바뀌고, React가 바뀐 부분만 다시 그려요.
  이런 방식을 SPA(Single Page Application)라고 해요. youtube.com도 이렇게 동작해요.

**새 개념: 공통 훅으로 반복 없애기 (`web/hooks/useAsync.ts`)**

"요청 → 기다림(로딩) → 응답 저장" 흐름이 페이지마다 반복돼요. 그래서 이 흐름을 훅 하나로 묶었어요.

```ts
const { data, loading } = useAsync(getVideo, videoId);
```

- `videoId`가 바뀌면 알아서 다시 요청해요.
- 응답이 늦게 오는 사이에 다른 영상으로 넘어가면, 늦게 온 옛 응답은 버려요.

**새 개념: 레이아웃 모드**

사이드바는 상황에 따라 세 가지 모양(variant)을 가져요.

| 모드 | 언제 | 모양 |
|---|---|---|
| `full` | 넓은 화면의 홈 | 240px 펼침 |
| `mini` | 좁은 화면의 홈 / 메뉴 접음 | 72px 아이콘만 |
| `drawer` | 시청 페이지, 모바일 | 숨겨 두고, 메뉴 버튼을 누르면 화면 위에 덮어서 열림 |

모드를 정하는 일은 `App.tsx` 한 곳에서만 해요. `Sidebar`는 전달받은 모드대로 그리기만 해요.

**참고:** 샘플 영상은 실제로는 10초짜리예요. 카드에 표시되는 길이(예: 57:03)는 가짜 데이터라서 실제 재생 길이와 달라요.

## 3단계 — 검색

**만든 것:** 헤더 검색창(자동완성, 키보드 ↑↓ 선택, 지우기 버튼), `/results?search_query=검색어` 검색 결과 페이지, 결과 없음 화면, 모바일 전용 검색 모드, 첫 자동 테스트

**새 개념: 검색 상태를 주소에 담기 (URL as State)**

```
검색창에 "요리" 입력 후 Enter
  → 주소가 /results?search_query=요리 로 바뀜
  → ResultsPage가 주소에서 검색어를 읽어 searchVideos("요리") 요청
  → 헤더 검색창도 주소에서 검색어를 읽어서 "요리"를 표시
```

- 검색어를 React 상태 변수가 아니라 **주소**에 저장해요.
  그래서 뒤로가기를 누르면 이전 검색어와 결과로 자연스럽게 돌아가요. 새로고침이나 링크 공유도 그대로 동작해요.
- 헤더와 결과 페이지는 서로 직접 값을 주고받지 않아요. 둘 다 **같은 주소를 읽을 뿐**이에요.
  주소가 두 컴포넌트가 함께 보는 "공유 저장소" 역할을 해요.

**새 개념: 비즈니스 로직을 순수 함수로 분리 (`core/search.ts`)**

- 검색 규칙은 모두 `core/search.ts`에 있어요. 모든 단어가 들어 있어야 결과에 포함되고, 제목에서 맞으면 점수가 더 높아요.
- 이 규칙은 화면과도, 데이터가 어디서 오는지와도 상관없는 **순수 함수**예요. 입력이 같으면 결과도 항상 같아요.
- 서비스 층(`videoService.searchVideos`)은 "데이터 가져오기 + 규칙 적용"을 이어 주기만 해요.
  나중에 서버가 생기면 검색 규칙은 서버로 옮기고, 서비스는 서버에 요청만 하게 바꾸면 돼요.

**새 개념: 자동 테스트 (`npm test`)**

- `core/*.test.ts` 파일이 "이 입력이면 이 결과가 나와야 한다"를 코드로 적어 둔 문서예요.
- `core/`는 순수 TypeScript라 브라우저 없이도 테스트할 수 있어요. 층을 나눈 덕분에 얻은 또 하나의 장점이에요.
- 지금 테스트는 9개이고, 모두 통과해요.

**새 개념: `key`로 컴포넌트 새로 만들기**

검색창은 내부에 입력 중인 글자를 상태로 갖고 있어요. 뒤로가기로 주소의 검색어가 바뀌면 검색창도 그 값으로 돌아가야 해요.
이때 `key={검색어}`를 주면, 검색어가 바뀔 때 React가 검색창을 아예 새로 만들어서 깨끗하게 초기화해요.
2단계에서 설명란 "더보기" 상태를 영상마다 초기화한 것도 같은 기법이에요.

## 4단계 — 좋아요, 구독, 댓글 (데이터 쓰기와 저장)

**만든 것:** 구독/구독중 버튼, 좋아요·싫어요 토글, 댓글 작성·삭제, 사이드바 구독 목록 연동. 새로고침해도 모두 유지돼요.

지금까지는 데이터를 **읽기만** 했어요. 이번 단계에서 처음으로 데이터를 **쓰고 저장**해요. 그래서 구조에 새 개념이 세 가지 생겼어요.

**새 개념 ①: 저장소 추상화 + 의존성 주입 (`core/storage.ts`)**

```
core/storage.ts          "getItem / setItem 할 수 있는 무언가"라는 약속(인터페이스)만 정의
        ▲ 끼워 넣기 (main.tsx에서 configureStore 호출)
web/platform/localStorageStore.ts    웹: 브라우저 localStorage
(나중에) native/asyncStorageStore.ts  모바일: React Native AsyncStorage
createMemoryStore()                    테스트: 메모리
```

- core는 "어디에" 저장되는지 몰라요. "저장할 수 있다"는 사실만 알아요.
- 실제 저장소는 앱이 시작할 때(`main.tsx`) 플랫폼이 끼워 넣어요. 이런 방식을 **의존성 주입**이라고 해요.
- AsyncStorage가 비동기라서 약속도 처음부터 `Promise`로 만들었어요. 모바일로 옮길 때 core는 한 줄도 바꿀 필요가 없어요.

**새 개념 ②: 전역 상태 (`core/userStore.ts`)**

구독 버튼은 시청 페이지에 있어요. 그런데 구독 목록은 사이드바에도 보여야 해요.
이렇게 **멀리 떨어진 여러 화면이 같은 데이터를 봐야 할 때** 전역 상태가 필요해요.

```
           ┌──────────── userStore (구독 목록, 좋아요 기록) ────────────┐
           │  subscribe(): "바뀌면 알려줘" 등록                         │
           │  getSnapshot(): 현재 값 읽기                               │
           │  toggleSubscription(), toggleRating(): 값 바꾸기 + 저장    │
           └───────▲───────────────────▲───────────────────▲──────────┘
                   │ 읽기/알림          │                   │
            SubscribeButton        RatingButtons         Sidebar
```

- 흐름: 버튼 클릭 → `userStore.toggleSubscription()` → 상태 변경 → 등록된 화면 전부에 알림 → 사이드바와 버튼이 동시에 다시 그려짐
- userStore도 React를 쓰지 않는 순수 TypeScript예요. React와는 `web/hooks/useUserStore.ts` 한 파일(`useSyncExternalStore`)로만 연결돼요.
  Redux나 Zustand 같은 상태 관리 라이브러리도 핵심 원리는 이것과 같아요.
- **낙관적 업데이트:** 저장이 끝날 때까지 기다리지 않고 화면부터 바꿔요. 그래서 버튼이 즉시 반응해요. YouTube도 이렇게 해요.
- **불변성:** 상태를 바꿀 때 기존 객체를 고치지 않고 매번 새 객체를 만들어요. 그래야 React가 "바뀌었다"를 알아챌 수 있어요.

**새 개념 ③: 전역 상태 vs 지역 상태 — 어디에 둘까?**

| 데이터 | 누가 보나 | 어디에 |
|---|---|---|
| 구독 목록 | 구독 버튼, 사이드바 (여러 곳) | 전역 (`userStore`) |
| 좋아요 기록 | 좋아요 버튼, (5단계) 좋아요 목록 페이지 | 전역 (`userStore`) |
| 댓글 | 그 영상의 댓글 영역만 | 지역 (`Comments` 컴포넌트 안) |
| 댓글 입력 중인 글자 | 입력창만 | 지역 (`CommentForm` 안) |

원칙: **필요한 곳 중 가장 가까운 곳에 둔다.** 모든 것을 전역에 두면 어디서 무엇이 바뀌는지 추적하기 어려워져요.

**새 개념 ④: 파생 상태 (Derived State)**

화면에 보이는 좋아요 수는 따로 저장하지 않아요. "원래 좋아요 수 + 내가 눌렀으면 1"로 **그때그때 계산**해요.
저장하는 값을 줄일수록 값끼리 서로 어긋나는 버그가 줄어요.

**테스트:** 구독 토글, 좋아요 취소/전환, 댓글 추가/삭제/빈 댓글 거부까지 테스트 15개가 모두 통과해요. 테스트에서는 메모리 저장소를 끼워 넣어서 실행해요. 의존성 주입 덕분에 이게 가능해요.

## 5단계 — 시청 기록, 재생목록, 구독 피드, 채널, 테마

**만든 것**

| 주소 | 페이지 | 데이터 출처 |
|---|---|---|
| `/feed/trending` | 인기 급상승 (조회수 순) | 서비스 |
| `/feed/subscriptions` | 구독 피드 (구독 채널의 최신 영상) | 전역 상태(구독 목록) + 서비스 |
| `/feed/history` | 시청 기록 (날짜별 묶음, 하나씩/전체 삭제) | 전역 상태(기록) + 서비스 |
| `/playlist?list=LL` | 좋아요 표시한 동영상 | 전역 상태(좋아요) + 서비스 |
| `/playlist?list=WL` | 나중에 볼 동영상 | 전역 상태(나중에 볼) + 서비스 |
| `/channel/:id` | 채널 페이지 | 서비스 |
| `/?category=게임` | 사이드바 "탐색" → 홈 카테고리 | 주소 |

그 밖에 영상 카드 ⋮ 메뉴(나중에 볼 동영상에 저장), 프로필 메뉴의 밝은/어두운 테마 전환, 사이드바 현재 위치 강조를 만들었어요.

**새 개념 ①: 같은 화면, 다른 데이터 출처 — 조합(Composition)**

"좋아요 표시한 동영상"과 "나중에 볼 동영상"은 화면이 똑같고, 영상 ID 목록을 어디서 가져오는지만 달라요.
그래서 `PlaylistPage` 하나가 주소의 `list` 값을 보고 출처만 바꿔요.

```
주소 list=LL → 전역 상태의 ratings에서 'like'만 골라 ID 목록 생성 ─┐
주소 list=WL → 전역 상태의 watchLater ID 목록 ─────────────────────┼→ getVideosByIds(ID 목록) → 같은 화면
```

목록형 화면(검색 결과, 인기 급상승, 시청 기록, 재생목록)도 모두 `VideoListItem` 하나를 함께 써요.
옵션(번호 표시, 작은 썸네일, 오른쪽 X 버튼)만 다르게 넘겨요. **작은 블록을 만들어 조합하는 것**이 컴포넌트 설계의 핵심이에요.

**새 개념 ②: 전역 상태는 "ID"만, 상세 정보는 서비스에서**

전역 상태에는 영상 ID와 시청 시각만 저장해요. 제목, 썸네일, 조회수 같은 상세 정보는 저장하지 않아요.
화면이 필요할 때 ID로 서비스에 다시 물어봐요(`getVideosByIds`).

- 장점: 영상 제목이 바뀌어도 기록에 옛 제목이 남지 않아요. **같은 정보를 두 곳에 복사해 두지 않는 것**(정규화)이 중요해요.
- 실제 서비스도 같아요. 사용자 기록에는 ID만 남기고, 상세 정보는 영상 API에서 받아와요.

**새 개념 ③: 테마 = 토큰 교체**

1.5단계에서 만든 디자인 토큰이 여기서 쓰여요.

```
프로필 메뉴 클릭 → userStore.setTheme('light') → 저장소에 기록
  → App이 <html data-theme="light"> 로 바꿈
  → CSS의 :root[data-theme='light'] 블록이 변수 값을 덮어씀
  → 컴포넌트는 하나도 안 바뀌었는데 앱 전체 색이 바뀜
```

모바일 앱으로 옮길 때도 원리는 같아요. 색 이름표(토큰)는 그대로 두고, 값 표만 플랫폼에 맞게 다시 만들면 돼요.

**새 개념 ④: 재사용 가능한 UI 동작 (`Menu`)**

"버튼을 누르면 뜨고, 바깥을 누르거나 Esc를 누르면 닫히는 팝업"은 여러 곳에서 필요해요(카드 ⋮, 프로필).
이 **동작**을 `Menu` 컴포넌트 하나에 담고, 어떤 버튼으로 열지와 어떤 항목을 보여줄지는 쓰는 쪽이 정해요.

**테스트:** 시청 기록 중복 제거, 날짜 묶음(오늘/어제/날짜), 나중에 볼 동영상 토글, 좋아요 목록 계산까지 테스트 20개가 모두 통과해요.

**① 진짜 서버 붙이기**

쇼츠, 실시간 스트리밍, 영상 업로드, 로그인, 알림, 답글. 이 기능들은 대부분 서버가 있어야 의미가 있어요.

## 6단계 — iOS·안드로이드 앱 (모노레포, 플레이어 오버레이, PiP·백그라운드 재생)

**만든 것:** YouTube iOS 앱 구조의 모바일 앱 (`apps/mobile`)

- 하단 탭(홈 · 쇼츠 · + · 구독 · 나), 상단 바(로고 · 전송 · 알림 · 검색), 칩
- 전체 화면 플레이어 ↔ 탭 바 위 미니 플레이어 (아래로 끌어서 접기)
- 자체 플레이어 컨트롤, 가로 스크롤 액션 버튼, 댓글 미리보기 카드 → 댓글 시트, 설명 시트
- PiP, 백그라운드 재생, 잠금 화면 "지금 재생 중" 표시

**새 개념 ①: 모노레포 (npm workspaces)**

```
packages/core    ← 순수 TypeScript      ┐
packages/hooks   ← React 훅 (DOM 없음)  ┼─ 두 앱이 함께 사용
apps/web         ← React DOM            ┘
apps/mobile      ← React Native
```

- 1~5단계에서 `core`를 React 없이 만들어 둔 덕분에, **모바일 앱에서 서비스·검색·전역 상태·댓글 코드를 한 줄도 다시 쓰지 않았어요.**
- 바뀐 건 두 가지예요.
  - 저장소 구현을 하나 더 만들었어요: `asyncStorageStore.ts`, 7줄.
  - 화면 컴포넌트를 React Native로 새로 그렸어요.
- `useAsync`, `useUserState`처럼 React는 쓰지만 브라우저는 쓰지 않는 훅은 `packages/hooks`로 옮겨서 함께 써요.

```
웹 main.tsx:          configureStore(localStorageStore); userStore.init();
모바일 _layout.tsx:    configureStore(asyncStorageStore); userStore.init();
                       ↑ 4단계에서 만든 "의존성 주입"이 실제로 쓰인 순간
```

**새 개념 ②: 플레이어는 "페이지"가 아니라 "오버레이"**

웹에서 시청 페이지는 `/watch/:id` 주소를 가진 **페이지**였어요. 그래서 다른 페이지로 가면 영상이 멈춰요.
YouTube 앱은 영상을 미니로 접은 채 다른 탭을 볼 수 있어요. 이게 가능하려면 플레이어가 **모든 화면 위에 따로 떠 있어야** 해요.

```
_layout.tsx
 ├─ Stack (탭, 검색, 채널, 재생목록 …)   ← 화면이 바뀌어도
 └─ PlayerOverlay                        ← 이건 계속 살아 있음 → 재생이 안 끊김

playerStore (core):  { videoId, mode: 'full' | 'mini' | null }
  영상 카드 누름 → playerStore.open(id)   (페이지 이동이 아님!)
  아래로 끌기    → playerStore.minimize()
  미니 누름      → playerStore.expand()
```

- 플레이어 엔진(`useVideoPlayer`)은 앱 전체에 **하나**만 만들고, 영상이 바뀌면 소스만 교체해요(`replaceAsync`).
- 크기 변화는 숫자 하나(`progress`: 0 = 전체, 1 = 미니)로 표현해요. 위치, 크기, 투명도를 모두 이 숫자에서 계산(interpolate)해요.
  손가락으로 끄는 동안에는 이 숫자를 직접 바꾸고, 손을 떼면 0이나 1로 스프링처럼 돌아가요.

**새 개념 ③: 네이티브 기능은 "설정 + 속성"으로 켠다**

| 기능 | 앱 설정 (app.json 플러그인 → 네이티브 설정 자동 생성) | 코드 |
|---|---|---|
| 백그라운드 재생 | `supportsBackgroundPlayback` → iOS `UIBackgroundModes: audio`, 안드로이드 포그라운드 서비스 | `player.staysActiveInBackground = true` |
| 잠금 화면 컨트롤 | (위와 같음) | `player.showNowPlayingNotification = true` + `metadata`(제목, 채널, 썸네일) |
| PiP | `supportsPictureInPicture` | `<VideoView allowsPictureInPicture startsPictureInPictureAutomatically>` |

- 네이티브 설정(Info.plist, AndroidManifest)을 손으로 고치지 않아요. `app.json`에 적으면 Expo가 빌드할 때 만들어 줘요.
  이 방식을 CNG(Continuous Native Generation)라고 해요.
- 설정이 바뀌면 앱을 **다시 빌드**해야 해요. 그래서 Expo Go 앱으로는 이 기능들을 확인할 수 없고, 개발 빌드(`npx expo run:ios`)가 필요해요.

**새 개념 ④: 같은 디자인 토큰, 다른 플랫폼**

`apps/mobile/src/theme/tokens.ts`는 웹 CSS 변수와 **같은 이름, 같은 값**이에요(`bg`, `text`, `surface` …).
웹은 CSS 변수를 바꾸고, 모바일은 토큰 객체를 바꿔요. 테마 값 자체는 `userStore` 하나가 관리해요.

**검증한 것 / 못 한 것**

- 확인함
  - 타입 검사, iOS·안드로이드 번들링(`expo export`) 성공
  - 네이티브 설정에 백그라운드 모드·PiP·포그라운드 서비스가 들어가는 것
  - 웹 버전으로 아이폰 크기 화면, 미니 플레이어, 끌어서 접기를 직접 눌러 보며 확인

  - 실제 아이폰에서 PiP, 백그라운드, 잠금 화면 동작 확인 (이 클라우드 환경에는 아이폰·Mac이 없어요)

## W2·W3 — YouTube 스타일 플레이어와 웹 미니 플레이어

**새 개념 ①: `<video>`는 앱 전체에 하나**

```
apps/web/src/player/
  playback.ts         하나뿐인 <video> + 그 상태를 React가 구독할 수 있게 감싼 스토어 + 조작 함수(controls)
  PlayerController    재생 엔진: 영상 교체, 시청 기록, 볼륨 기억, 미디어 세션, 페이지 이탈 시 미니로 전환
  PlayerSlot          <video>를 "이 자리에 꽂아 줘" — 시청 페이지와 미니 플레이어가 각자 하나씩 가짐
  FullPlayer          큰 플레이어 UI: 컨트롤 바, 진행 막대, 설정, 단축키, 다음 영상 카운트다운
  MiniPlayer          오른쪽 아래 작은 플레이어
```

- 모바일 앱에서는 "모든 화면 위에 떠 있는 오버레이"로 플레이어를 유지했어요.
- 웹에서는 다른 방법을 썼어요. **하나뿐인 `<video>` 요소를 필요한 자리로 옮겨요(PlayerSlot).**
  - 시청 페이지가 있으면 그 자리로, 없으면 미니 플레이어 자리로 옮겨요.
  - 요소 자체가 그대로라서 소리, 버퍼, 재생 위치가 모두 유지돼요.
- 두 플랫폼 모두 "지금 무슨 영상을 어떤 크기로 보는가"는 `core`의 `playerStore` 하나로 관리해요.

**새 개념 ②: 브라우저 요소를 React 상태처럼 쓰기**

`<video>`는 React가 만든 게 아니라 브라우저 객체예요. 그래서 이벤트(play, timeupdate, volumechange …)를 들을 때마다 스냅샷을 새로 만들어요.
그리고 4단계 `userStore`와 똑같이 `useSyncExternalStore`로 연결해요.

**외부 상태를 React에 연결하는 방법은 이것 하나로 통일돼 있어요.** 사용자 데이터, 플레이어 모드, 비디오 요소 모두 같아요.

**새 개념 ③: 조작 함수를 한곳에 (`controls`)**

재생/일시정지, 건너뛰기, 볼륨 같은 조작은 `controls` 객체 하나에 모아 뒀어요.
버튼, 키보드 단축키, 미디어 세션(키보드 미디어 키·잠금 화면)이 모두 같은 함수를 불러요.
그래서 "10초 건너뛰기" 동작을 고칠 때 한 곳만 고치면 돼요.

**사용자 설정 기억:** 볼륨, 음소거, 자동재생, 영화관 모드는 `userStore.playerPrefs`에 저장해요(재생 속도는 YouTube처럼 기억하지 않아요).
설정은 core에 있어서 나중에 모바일 앱도 같은 설정을 써요.

**단축키:**

| 키 | 동작 |
|---|---|
| K / Space | 재생·일시정지 |
| J / L | 10초 뒤로 / 앞으로 |
| ← / → | 5초 뒤로 / 앞으로 |
| ↑ / ↓ | 볼륨 5% |
| M | 음소거 |
| F | 전체 화면 |
| T | 영화관 모드 |
| I | 미니 플레이어 |
| 0~9 | 영상의 0%~90% 지점으로 |
| Shift+N | 다음 영상 |
| > / < | 재생 속도 |

**겪은 문제와 해결:** 시청 페이지가 사라지는 렌더와 미니 플레이어가 나타나는 렌더가 서로 달라요. 그 사이 `<video>`가 잠깐 문서에서 빠지면 브라우저가 자동으로 일시정지해요.
그래서 `PlayerSlot`이 빠질 때 재생 중이었는지 기억했다가, 새 자리에 꽂히면 다시 재생하게 했어요.

## W4 — 휴대폰 화면 = YouTube 모바일 레이아웃, Shorts

**새 개념 ①: 같은 컴포넌트, 화면 폭에 따라 다른 배치**

- 대부분은 **CSS 미디어쿼리**로 처리해요. 하단 메뉴 표시, 미니 플레이어를 막대 모양으로, 카드 정보를 한 줄로 바꾸는 것 등이에요.
- 구조 자체가 달라야 할 때만 JS(`useMediaQuery`)로 다른 컴포넌트를 골라요.
  - 추천 영상: 데스크톱은 작은 가로 카드, 휴대폰은 큰 카드
  - 댓글: 데스크톱은 바로 펼침, 휴대폰은 접힌 카드
- 원칙: **모양 차이는 CSS로, 구조 차이만 JS로.**

**새 개념 ②: `position: sticky`의 범위**

휴대폰에서 플레이어를 화면 위에 붙여 두려고 `sticky`를 썼는데, 처음엔 스크롤하면 사라졌어요.
sticky는 **부모 상자 안에서만** 붙어 있기 때문이에요. 플레이어의 부모(왼쪽 칸)가 추천 목록보다 먼저 끝나서 그랬어요.
휴대폰에서는 왼쪽 칸을 `display: contents`로 "투명한 상자"로 만들어 해결했어요. 그러면 플레이어의 부모가 페이지 전체가 돼요.

**새 개념 ③: Shorts는 메인 플레이어와 다른 설계**

- Shorts는 영상 여러 개를 위아래로 넘겨요. 그래서 메인 플레이어처럼 `<video>` 하나를 옮겨 쓰지 않고, **각 Shorts가 자기 `<video>`를 가져요.**
- 대신 `IntersectionObserver`로 화면에 70% 이상 보이는 영상만 재생하고, 나머지는 멈춰요.
- 넘기는 동작은 JS 없이 CSS `scroll-snap`으로 만들어요.
- Shorts에 들어가면 메인 플레이어(미니 플레이어 포함)는 닫아요. 소리가 겹치지 않게 하려는 거예요.
- 어떤 영상이 Shorts인지는 `core`의 `getShorts()`가 정해요. 규칙은 60초 이하예요. 화면은 규칙을 몰라도 돼요.
